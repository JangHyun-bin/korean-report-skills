# 첫 화면의 시각 정체성 — 로고와 배너

- **일자** — 2026-08-10
- **상태** — 구현 완료. Pages 관련 부분은 이후 철회
- **영향 범위** — `README.md` 머리, `docs/assets/`, CI

---

> **이후 변경 (2026-08-10)** — 이 문서가 규정한 것 중 **GitHub Pages 관련 부분은
> 실현되지 않았다.** 구현 직후 Pages 를 전면 제거하기로 결정하여 사이트·워크플로·
> 색인(`pages-index.html`)이 모두 없어졌다. 아래에서 그것들을 가리키는 대목은
> 이력으로 읽고 따르지 않는다. 파비콘 자산 자체는 남아 있다.
> Codex 는 이 저장소를 파일 추가 없이 마켓플레이스로 인식한다는 것이 뒤에 확인되었다.

## 맥락

README 를 문제 중심으로 다시 쓴 뒤에도 첫 화면에 **시각 앵커가 없었다.**
로고도 뱃지도 배너도 없이 제목과 문단으로 시작한다.

이 저장소는 **문서 조판 도구**다. 첫 화면이 볼품없으면 그 자체가 반증이 된다.
같은 이유로 이미 한 번 지적받았다 — 규약을 가르치는 문서가 자기 규약을 어기고 있었고,
`tests/test_own_prose.py` 로 막았다. 시각도 같은 문제다.

참조로 삼은 두 저장소(Awesome Systematic Trading · OpenChamber)는 같은 여섯 요소를 쓴다.

| 요소 | 역할 |
|---|---|
| 시각 앵커 | 배너 또는 로고. 5초 안에 성격을 전달한다 |
| 뱃지 행 | 신뢰 신호 — 검사·릴리스·라이선스 |
| 태그라인 | 무엇인지 한 줄 |
| 짧은 설명 | 두 문단 이내 |
| 결과물 증거 | 실제 스크린샷 |
| 숫자 | 규모를 즉시 전달 |

우리에게는 **결과물 증거**만 있었다.

## 결정

### 1. 구조 — 로고와 배너의 겹침

OpenChamber 계열이다. 질문형 제목이 태그라인 자리를 그대로 차지하므로
지금 README 구조와 충돌하지 않는다.

```
[로고] korean-report-skills        워드마크 행
[뱃지 행]
# 왜 Claude가 만든 한국어 문서는 어딘가 이상할까    태그라인 겸 h1
설명 2문단
[결과물 배너]
[캡션 한 줄]
```

### 2. 로고 — 절 표제

`design.md` §2.2 가 규정하는 paper 모드의 시각 서명을 잘라낸 형태다.
파란 절 번호 + 잉크 제목 + 굵은 괘선 + 옅은 본문 두 줄.

**로고가 곧 디자인 시스템의 요약이다.** 로고를 본 사람은 이미 조판 규약 하나를 본 셈이다.
새로 발명한 것이 아니라 규정된 것을 잘라냈으므로 문서와 로고가 어긋날 수 없다.

로고도 디자인 시스템을 지킨다 — **액센트 한 색, 그림자 없음, 두 번째 색조 없음.**
회색은 잉크의 투명도로만 표현한다.

#### 축소 3단

하나의 마크로 16px 까지 버티려 하면 큰 크기가 빈약해진다.
같은 문법의 축약판을 크기별로 갈아끼운다.

| 크기 | 마크 | 구성 |
|---|---|---|
| ≥ 40px | **V2** | 번호 + 제목 + 굵은 괘선 + 본문 2줄 |
| 24–32px | **V4** | 번호 + 제목 + 괘선 |
| 16px | **V6** | 번호 + 괘선 |

축소 시험에서 확인한 것 — **굵은 괘선이 형태를 고정한다.** 괘선이 가는 판(V1)은
24px 이하에서 본문 줄이 회색 얼룩으로 뭉개지는데, V2 는 「제목 + 밑줄」 뼈대가 유지된다.

#### 자산 명세

viewBox 는 `0 0 100 100`, 여백을 꽉 채운다. 원안은 마크가 좁게 앉아
40px 로 줄이면 실제 획이 15px 밖에 되지 않았다.

GitHub 라이트·다크에서 같은 파일이 따라가야 한다. 다만 **`currentColor` 로는 되지 않는다** —
SVG 가 `<img src>` 로 불릴 때는 부모의 `color` 를 상속할 대상이 없다.
파일 안에 `<style>` 을 두고 `@media (prefers-color-scheme: dark)` 로 색을 전환한다.

`favicon.svg` 는 Pages 를 걷어낸 뒤 저장소 안에서 그것을 가리키는 곳이 없다.
**지우지 않는다** — 축소 3단의 최소판이고, 16px 대역을 이 문법으로 채우는
유일한 자산이다. 다음에 파비콘이 필요한 자리가 생기면 그대로 쓴다.

```
V2 (logo.svg)
  rect  4, 8,17,17 r3.5  primary
  rect 27, 8,61,17 r3.5  ink
  rect  4,38,92,14 r7    ink
  rect  4,66,92, 7 r3.5  ink 42%
  rect  4,83,62, 7 r3.5  ink 42%

V4 (logo-sm.svg)
  rect  4,20,22,22 r4.5  primary
  rect 33,20,63,22 r4.5  ink
  rect  4,60,92,13 r6.5  ink

V6 (favicon.svg)
  rect  6,16,30,30 r6    primary
  rect  6,62,88,18 r9    ink
```

라이트에서 `ink #1d1d1f` · `primary #0066cc`, 다크에서 `ink #fff` · `primary #2997ff`.

### 3. 배너 — 겹침

문서 세 장을 비스듬히 겹친다. 가운데를 앞에 두어 대비를 형성한다.

| 자리 | 조각 | 성격 |
|---|---|---|
| 좌·뒤 | paper 표지 (머리글 + 초록 + 배지 범례) | 흰 종이 |
| 중앙·앞 | deck 다크 타일 (대비막대 도해) | 검은 화면 |
| 우·뒤 | paper 본문 (메트릭 카드 + 타임라인) | 흰 종이 |

**세 조각이 전부 달라야 한다.** 초기 시안은 같은 이미지를 두 번 썼다.

높이 300px, 문서는 배너 아래로 잘려 나가게 둔다 — 문서가 계속된다는 뜻으로 읽힌다.

#### 다크 대응

흰 종이가 다크에서 뜨는 것은 문제가 아니다. **배경만 어둡게 바꾸면**
종이가 어둠 위에 떠 있는 것으로 읽혀 자연스럽고, 가운데 다크 타일과 대비가 생겨
「두 모드가 있다」가 한 장에서 전달된다.

라이트·다크 두 벌을 만들어 `<picture>` 로 전환한다.

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/assets/banner-dark.png">
  <img src="docs/assets/banner-light.png" alt="...">
</picture>
```

배경 — 라이트 `#f7f8fa → #eef1f5`, 다크 `#161b22 → #0d1117` (GitHub 배경에 정합한다).
종이 테두리는 헤어라인 한 겹과 아주 옅은 그림자만 쓴다.
`design.md` §1.4 는 문서에 그림자를 금지하지만, 배너의 종이는 **문서가 아니라 문서의 사진**이므로
겹침을 읽히게 하는 최소한의 깊이는 허용한다.

배너 아래에 캡션 한 줄을 둔다.

> paper(세로·보고서) · deck(가로·협의자료) — 전부 HTML 파일 하나로 완결됩니다

### 4. 뱃지

`tests` · `release` · `plugin` · `license` 넷.

**뱃지는 GitHub 관용 색을 따른다.** 단일 액센트 규칙은 **문서에만** 적용된다.
뱃지를 파랑 일색으로 만들면 서로 구별되지 않아 읽기 비용이 상승한다.
문서와 저장소 껍데기는 다른 장르다 — README 본문이 §1.1 을 따르지 않는 것과 같은 이유다.

## 배너의 재생성

지금 배너는 실제 문서에서 잘라낸 것이다. **문서가 바뀌면 배너가 낡는다.**
스크린샷을 손으로 갱신하는 저장소는 반드시 어긋난다.

예시 문서와 같은 방식으로 CI 가 매번 재생성한다.

```
examples/build_example.py → mathbuild.js → 조각 캡처 → 배너 합성 → docs/assets/
```

조각 캡처와 합성은 `scripts/build-banner.py` 가 맡는다.
합성은 HTML 레이아웃을 렌더해서 찍는다 — 이미지 편집 라이브러리를 새로 들이지 않는다.

## 검사

- 로고 SVG 3종이 실재하고 `viewBox="0 0 100 100"` 인지
- SVG 안의 색이 규격 네 가지(액센트 라이트·다크, 잉크 라이트·다크)뿐인지
  — 다크 대응은 파일 안 `@media` 로 하므로 hex 리터럴 자체는 정상이다
- README 가 가리키는 배너 두 벌이 실재하는지
- `<picture>` 에 `prefers-color-scheme: dark` source 가 있는지
- 배너가 예시 문서보다 낡지 않았는지 (CI 가 재생성하므로 diff 가 나면 실패)

## 검토한 대안

### 로고 심볼

| 후보 | 탈락 사유 |
|---|---|
| 원고지 격자 | 정체성은 가장 선명하나 손글씨·학창시절 정서가 기술 문서 도구와 어긋난다 |
| 두 모드 (세로·가로 사각형) | 안전하지만 흔한 형태라 기억에 남지 않는다 |
| 브래킷 `⟦ ⟧` | 16px 에서 가장 선명했으나 한국어 도구라는 신호가 없다 |
| 중간점 | 가장 절제되어 있으나 의미가 가장 약하다 |
| 교정 부호 | 관습적으로 빨강인데 우리 팔레트에 두 번째 색조가 없다 |

### 배너 배치

| 후보 | 탈락 사유 |
|---|---|
| 가로 스트립 | 각각은 잘 보이나 밋밋하다 |
| 다크 전면 | 라이트 테마에서 검은 덩어리가 화면을 압도한다 |
| 한 장 + 디테일 | 정보는 많으나 겹침만큼 풍성해 보이지 않는다 |
| 테마별 전환 (라이트=paper, 다크=deck) | 영리하지만 한 번에 하나만 보이고, 테마를 바꾸지 않는 사람은 두 모드가 있다는 것을 끝까지 모른다 |

마지막 안의 `<picture>` 기법은 버리지 않고 **같은 배너의 라이트·다크 두 벌**에 쓴다.
